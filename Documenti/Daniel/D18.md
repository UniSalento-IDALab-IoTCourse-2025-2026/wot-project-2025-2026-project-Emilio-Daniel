# D18 - Spiegazioni AI normalizzate nel backend

Questo documento riassume il lavoro fatto per il punto D18 della scaletta di Daniel.
L'obiettivo e' rendere stabile e leggibile la spiegazione dell'indice AI per la dashboard,
anche se il payload prodotto dall'Edge cambia forma o contiene nomi tecnici.

## Endpoint aggiornati

La nuova spiegazione normalizzata viene restituita in:

```text
GET /api/v1/patients/{patient_id}/current
GET /api/v1/patients/{patient_id}/decisions
GET /api/v1/telemetry/patients/{patient_id}/decisions
```

Il campo aggiunto e':

```text
ai_explanation
```

I campi gia' presenti restano invariati, quindi la dashboard esistente continua a
funzionare.

## Campi principali

```json
{
  "previous_score": 40.0,
  "score_delta": 32.5,
  "score_direction": "aumento",
  "updated_at": "2026-07-15T10:00:00Z",
  "model_label": "generic_wearable_anomaly_only",
  "data_reliability": {
    "level": "media",
    "ratio": 0.58,
    "available_features": 7,
    "expected_features": 11,
    "imputed_features": 2,
    "quality_status": "warning"
  },
  "positive_factors": [],
  "negative_factors": [],
  "missing_or_imputed_features": [],
  "model_contributions": {},
  "message": "Supporto al triage: la decisione finale resta al medico."
}
```

## Cosa viene calcolato

### Previous score e delta

Il backend cerca la decisione precedente dello stesso paziente e calcola:

- `previous_score`;
- `score_delta`;
- `score_direction`.

La direzione puo' essere:

```text
aumento
diminuzione
stabile
non_disponibile
```

### Feature leggibili

Le feature tecniche vengono convertite in etichette leggibili:

```text
heart_rate_mean -> Frequenza cardiaca media
spo2_mean -> Saturazione media SpO2
kitchen_minutes -> Permanenza in cucina
room_changes -> Cambi stanza
```

Ogni feature mantiene anche:

- valore rilevato;
- valore usato dal modello dopo preprocessing;
- unita';
- z-score;
- impatto;
- direzione rispetto al riferimento;
- modello sorgente;
- flag `imputed`.

### Fattori positivi e negativi

Il backend separa:

- `positive_factors`: valori sopra il riferimento;
- `negative_factors`: valori sotto il riferimento.

Questa separazione serve al frontend per spiegare cosa ha contribuito all'aumento o alla
riduzione dell'indice, senza dover interpretare direttamente gli z-score.

### Missingness e imputazione

Il campo `missing_or_imputed_features` contiene i dati:

- mancanti nella finestra;
- oppure imputati dal modello.

I valori mancanti non vengono trasformati in zero.

### Affidabilita' del dato

`data_reliability` combina:

- quante feature attese sono disponibili;
- quante feature sono imputate;
- qualita' dell'ultima decisione (`ok`, `warning`, `error`).

Il livello risultante e':

```text
alta
media
bassa
```
