# D12 - Deployment e osservabilita'

## Obiettivo

La D12 chiude la parte Cloud rendendo backend, database, broker MQTT e worker avviabili in modo ordinato per sviluppo, demo e futura produzione.

Architettura di avvio:

```text
Docker Compose
  -> Mosquitto MQTT
  -> PostgreSQL
  -> Migrazioni Alembic
  -> Backend FastAPI
  -> Worker MQTT backend
```

## Avvio con Docker Compose

Preparare i file locali:

```powershell
Copy-Item cloud\.env.example cloud\.env
Copy-Item cloud\backend\.env.example cloud\backend\.env
```

Poi inserire nei due `.env` le password locali. Questi file sono ignorati da Git.

Avvio completo Cloud:

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT\cloud
docker compose up -d mqtt postgres backend backend-mqtt-worker
```

Il servizio `backend-migrations` viene eseguito automaticamente prima del backend e applica:

```powershell
python -m alembic upgrade head
```

Quindi, con Compose completo, non bisogna lanciare a mano le migrazioni ogni volta.

## Configurazioni development, test e production

File disponibili:

```text
cloud/backend/.env.example
cloud/backend/.env.test.example
cloud/backend/.env.production.example
```

Regole:

- `development`: demo locale, dashboard su localhost, eventuali utenti demo;
- `test`: test automatici e Firebase fake;
- `production`: niente demo auth, niente Firebase fake, CORS ristretto a domini reali, segreti forti obbligatori.

Il backend blocca l'avvio in produzione se trova placeholder `CAMBIA_...` nei segreti principali.

## HTTPS e WSS

Il backend resta HTTP dentro la rete interna. In produzione HTTPS e WSS vanno messi davanti con reverse proxy.

Template:

```text
cloud/deploy/nginx.example.conf
```

Il file mostra redirect HTTPS, proxy verso backend su porta 8080 e supporto WebSocket per `/ws/v1/`.

## Raspberry Pi 5 e systemd

Su RPi5 gli script PowerShell non vengono usati. Per Linux sono presenti gli equivalenti
senza estensione:

```text
Script/avvio/backupPostgres
Script/avvio/ruotaLogCloud
Script/test/test_cloud_smoke
```

Per avviare automaticamente lo stack Cloud su Raspberry:

```bash
chmod +x Script/avvio/backupPostgres Script/avvio/ruotaLogCloud Script/test/test_cloud_smoke
sudo cp cloud/deploy/iot-cloud-stack.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now iot-cloud-stack.service
sudo systemctl status iot-cloud-stack.service
```

Per backup automatico giornaliero:

```bash
sudo cp cloud/deploy/iot-cloud-backup.service /etc/systemd/system/
sudo cp cloud/deploy/iot-cloud-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now iot-cloud-backup.timer
systemctl list-timers | grep iot-cloud-backup
```

I file systemd assumono che il progetto sia in:

```text
/home/pi/progetto-iot
```

Se la cartella cambia, modificare `WorkingDirectory` ed `ExecStart` nei file `.service`.

## Rollback

Rollback applicativo:

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT
git checkout <commit-precedente>
cd cloud
docker compose build backend backend-mqtt-worker
docker compose up -d backend backend-mqtt-worker
```

Rollback database:

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT\cloud\backend
.\.venv\Scripts\python -m alembic downgrade -1
```

Se il problema riguarda dati corrotti, fermare backend e worker e ripristinare un backup PostgreSQL.

## Controllo segreti

Prima del commit:

```powershell
git status --short
git diff -- .gitignore cloud\.env.example cloud\backend\.env.example
```

Non devono comparire:

- `cloud/.env`;
- `cloud/backend/.env`;
- `cloud/firebase/service-account.json`;
- certificati reali;
- password MQTT/PostgreSQL/Firebase;
- token Google Health o FCM.

`.gitignore` ignora gia' questi file.
