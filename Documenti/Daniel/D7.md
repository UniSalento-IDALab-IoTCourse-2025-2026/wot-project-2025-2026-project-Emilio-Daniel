# D7 - Autenticazione, autorizzazione e audit

## Obiettivo

Il blocco D7 chiude la parte di sicurezza applicativa del backend Cloud:

- login reale con password salvate come hash;
- access token breve per REST e WebSocket;
- refresh token revocabile;
- ruoli separati per medico, caregiver, paziente e admin;
- accesso ai soli pazienti autorizzati;
- audit delle azioni importanti.

In questo modo la dashboard medico, l'app paziente e in futuro l'app caregiver non leggono dati fuori dal proprio perimetro.

## Scelte fatte

### Password

Le password non vengono salvate in chiaro. Il backend usa PBKDF2-SHA256 con salt casuale:

```text
pbkdf2_sha256$iterazioni$salt$hash
```

Questo significa che nel database non compare mai la password reale.

### Access token

Il login restituisce un access token breve. La dashboard lo invia nelle chiamate REST:

```http
Authorization: Bearer <access_token>
```

Lo stesso token viene usato anche dalla WebSocket:

```text
ws://127.0.0.1:8080/ws/v1/patients/patient-001?token=<access_token>
```

Se manca il token, oppure il token non consente di leggere quel paziente, la connessione WebSocket viene chiusa.

### Refresh token

Il refresh token serve a ottenere un nuovo access token senza rifare login. Nel database viene salvato solo l'hash del refresh token, così se il database viene letto da qualcuno non si possono usare direttamente i token.

Endpoint:

```text
POST /api/v1/auth/refresh
POST /api/v1/auth/logout
```

Il logout revoca il refresh token. L'access token resta breve e scade da solo.

### Ruoli

Sono previsti questi ruoli:

| Ruolo | Cosa puo' fare |
| --- | --- |
| doctor | Legge i pazienti assegnati, crea task, prende in carico e risolve alert |
| caregiver | Legge i pazienti assegnati e prende in carico alert |
| patient | Legge solo se stesso e invia risultati dei task |
| admin | Ha accesso amministrativo completo |

## Utenti demo locali

In ambiente `development` e `test` il backend puo' creare utenti demo, ma solo se
sono abilitati nel `.env` locale. Le credenziali non devono stare nel codice e non
devono essere committate.

Configurazione locale:

```text
IOT_BACKEND_DEMO_AUTH_ENABLED=true
IOT_BACKEND_DEMO_AUTH_PASSWORD=<password locale non committata>
IOT_BACKEND_DEMO_DOCTOR_EMAIL=<email medico locale>
IOT_BACKEND_DEMO_CAREGIVER_EMAIL=<email caregiver locale>
IOT_BACKEND_DEMO_PATIENT_EMAIL=<email paziente locale>
IOT_BACKEND_DEMO_ADMIN_EMAIL=<email admin locale>
```

Questi utenti sono pensati solo per sviluppo locale. In produzione bisogna creare utenti reali, disattivare il demo auth e cambiare `IOT_BACKEND_AUTH_SECRET_KEY`.

## Permessi implementati

Il backend filtra i pazienti usando le associazioni nel database:

- `doctor_patients` per i medici;
- `caregiver_patients` per i caregiver;
- `patient_users` per il paziente;
- admin senza filtro.

Sono protetti:

- lista pazienti;
- `/current`;
- finestre feature;
- decisioni AI;
- alert;
- task;
- system status;
- WebSocket realtime.

## Audit

Il backend registra eventi audit per:

- login;
- logout;
- creazione task;
- completamento task;
- presa in carico alert;
- risoluzione alert.

Gli endpoint amministrativi completi non sono ancora stati aggiunti, ma e' gia'
presente l'helper `write_audit(...)` da riusare quando creeremo quelle modifiche.

Nei log audit non vengono scritti:

- password;
- access token;
- refresh token;
- token Google Health;
- token FCM.

## Revoca dispositivo smarrito

Se un dispositivo viene perso o rubato:

1. revocare il refresh token collegato al dispositivo;
2. attendere la scadenza dell'access token breve;
3. se necessario disattivare l'utente impostando `users.is_active = false`;
4. cambiare password all'utente.

In sviluppo si puo' usare:

```powershell
POST /api/v1/auth/logout
```

passando il refresh token da revocare.
