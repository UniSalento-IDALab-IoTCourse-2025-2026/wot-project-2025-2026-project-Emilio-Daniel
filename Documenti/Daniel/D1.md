# D1 - Broker MQTT Cloud

Questo documento riassume tutto quello che e' stato fatto per il punto D1 della scaletta
di Daniel: scelta del broker MQTT, configurazione locale, TLS, WSS, ACL, utenti, test e
procedura per aggiungere nuovi pazienti.

## Obiettivo

Il broker MQTT deve permettere questo flusso:

```text
Raspberry/Edge paziente -> MQTT broker -> backend Cloud -> dashboard/app
backend Cloud -> MQTT broker -> Raspberry/Edge paziente
```

Il Raspberry pubblica eventi, finestre, decisioni, stato sensori e alert. Il backend legge
questi eventi, li salva e li rende disponibili a dashboard medico, app paziente e
caregiver. Il backend puo' anche inviare comandi verso il Raspberry.

## Scelta fatta

Abbiamo scelto:

```text
Mosquitto in Docker
```

Motivi:

- e' semplice da avviare in locale su Windows;
- puo' essere spostato su VPS/Cloud senza cambiare tecnologia;
- supporta username/password, ACL, TLS, WSS, QoS, retained message, persistence e Last Will;
- e' adatto sia per sviluppo sia per una prima versione reale del sistema;
- si integra bene con Raspberry Pi 5, backend Python/FastAPI e dashboard.

## Porte configurate

```text
1883 -> MQTT locale con username/password
8883 -> MQTT protetto da TLS
9001 -> MQTT over secure WebSockets, cioe' WSS
```

La porta `1883` serve per test veloci in locale. La porta `8883` e' quella corretta per
ambiente Cloud/VPS. La porta `9001` serve solo se in futuro un client Web deve parlare
direttamente MQTT over WebSocket. La dashboard principale dovrebbe comunque usare il
backend tramite API REST e WebSocket applicativo, non MQTT diretto.

## Utenti MQTT

Abbiamo creato tre utenti per lo sviluppo:

```text
edge_patient_001 -> Raspberry/Edge del paziente 001
backend          -> backend Cloud
mqtt_test        -> client manuale di test
```

Logica scelta:

```text
1 paziente = 1 Raspberry/Edge = 1 utente MQTT dedicato
```

Questa scelta e' importante per sicurezza: se il Raspberry del paziente 001 viene
compromesso, non deve poter pubblicare dati fingendosi il paziente 002.

## ACL

Le ACL sono in:

```text
cloud/mqtt/aclfile
```

Regola:

```text
edge_patient_001 -> puo' pubblicare solo sui topic di patient-001
backend          -> puo' leggere tutti i pazienti e pubblicare comandi autorizzati
mqtt_test        -> puo' fare test solo su patient-001
```

Esempio attuale:

```text
user edge_patient_001
topic write iot/patients/patient-001/edge/status
topic write iot/patients/patient-001/telemetry/window
topic write iot/patients/patient-001/telemetry/decision
topic write iot/patients/patient-001/alerts/critical
topic write iot/patients/patient-001/sensors/watch
topic write iot/patients/patient-001/sensors/ble
topic read iot/patients/patient-001/commands/#

user backend
topic read iot/patients/+/edge/status
topic read iot/patients/+/telemetry/#
topic read iot/patients/+/alerts/#
topic read iot/patients/+/sensors/#
topic write iot/patients/+/commands/#
```

Il simbolo `+` significa "un solo livello qualsiasi". Quindi il backend puo' leggere:

```text
iot/patients/patient-001/...
iot/patients/patient-002/...
iot/patients/patient-003/...
```

Gli Edge invece non usano `+`, perche' devono restare bloccati sul proprio paziente.

## Certificati TLS locali

Su Windows non avevamo `openssl` installato, quindi abbiamo usato Docker.

Generare certificato locale self-signed:

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT

docker run --rm `
  -v ${PWD}\cloud\mqtt\certs:/certs `
  alpine/openssl req -x509 -newkey rsa:2048 -days 365 -nodes `
  -keyout /certs/server.key `
  -out /certs/server.crt `
  -subj "/CN=localhost" `
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

Copiare il certificato come CA locale:

```powershell
Copy-Item cloud\mqtt\certs\server.crt cloud\mqtt\certs\ca.crt -Force
```

Sistemare i permessi per permettere a Mosquitto di leggere la chiave:

```powershell
docker run --rm `
  -v ${PWD}\cloud\mqtt\certs:/certs `
  alpine chmod 644 /certs/ca.crt /certs/server.crt /certs/server.key
```

In produzione questi certificati self-signed vanno sostituiti con certificati reali del
dominio/VPS.

## Last Will

Il Last Will serve per segnalare una disconnessione improvvisa del Raspberry.

Esempio concettuale:

```text
topic: iot/patients/patient-001/edge/status
event_type: edge_offline_unexpected
payload.online: false
payload.reason: mqtt_last_will
```

Se il Raspberry si scollega male, Mosquitto pubblica automaticamente quel messaggio. Il
backend lo usera' per aggiornare lo stato tecnico del paziente.

## Retained message

Policy scelta:

```text
retained consentito solo per stato corrente / online-offline
retained non usato per finestre, decisioni, alert o dati sanitari
```

Motivo:

- lo stato corrente e' utile per un client che si collega dopo;
- finestre, decisioni e alert devono essere salvati dal backend con `message_id` e
  timestamp;
- non vogliamo che un client riceva una decisione vecchia solo perche' e' rimasta retained.

Nota tecnica: Mosquitto con semplice file ACL non blocca retained per singolo topic. Quindi
la regola viene applicata dai publisher del progetto e verificata dallo script di test.

## Dashboard medico con piu' pazienti

Il medico non si collega direttamente a MQTT.

Flusso corretto:

```text
MQTT broker -> backend -> database -> dashboard medico
```

Il backend legge tutti i pazienti dal broker, ma la dashboard mostra solo i pazienti
assegnati al medico nel database. Questo filtro non deve stare nel broker MQTT, ma nel
backend/API.

## Revoca credenziali

Se un Raspberry viene perso, sostituito o compromesso:

1. cambiare o rimuovere la password dell'utente Edge in `cloud/mqtt/passwd`;
2. riavviare Mosquitto;
3. aggiornare il Raspberry autorizzato con le nuove credenziali;
4. verificare che il vecchio client non riesca piu' a pubblicare;
5. registrare l'evento nel backend/audit quando questa parte sara' implementata.

## Rinnovo certificati

In locale:

```text
certificati self-signed in cloud/mqtt/certs/
```

In produzione:

```text
certificati validi per il dominio pubblico del broker
```

Procedura:

1. generare/rinnovare `server.crt` e `server.key`;
2. aggiornare `ca.crt` se cambia la CA;
3. sostituire i file in `cloud/mqtt/certs/`;
4. riavviare Mosquitto;
5. testare connessione su `8883`;
6. annotare data di scadenza e prossima rotazione.
