# D4 - Subscriber MQTT e ingestione

Questo documento riassume il punto D4 della scaletta di Daniel: collegare il backend al
broker MQTT, validare i payload ricevuti dall'Edge e salvarli nel database PostgreSQL.

## Obiettivo

Il backend deve ascoltare i messaggi pubblicati dal Raspberry Pi 5 e trasformarli in
righe persistenti nel database.

Flusso:

```text
Raspberry Pi 5
-> MQTT/TLS
-> backend subscriber
-> validazione payload
-> PostgreSQL
-> eventi interni per WebSocket/API future
```

## Scelte fatte

Abbiamo scelto un subscriber dentro lo stesso backend FastAPI, non un microservizio
separato.

Motivi:

- il progetto e' ancora nella prima versione e un backend unico e' piu' semplice da
  avviare, testare e spiegare;
- il subscriber usa gli stessi modelli SQLAlchemy e la stessa configurazione del backend;
- in futuro si potra' separare il worker solo se carico o deployment lo richiederanno.

La libreria usata per MQTT e':

```text
paho-mqtt
```

## Topic ascoltati

Il backend si iscrive a questi topic:

```text
iot/patients/+/edge/status
iot/patients/+/telemetry/window
iot/patients/+/telemetry/decision
iot/patients/+/alerts/critical
iot/patients/+/sensors/watch
iot/patients/+/sensors/ble
```

Il `+` indica che il backend puo' ricevere messaggi di tutti i pazienti autorizzati.
Le ACL del broker impediscono invece al singolo Edge di pubblicare sui topic di altri
pazienti.

## Validazione

Ogni payload deve contenere almeno:

```text
schema_version
message_id
event_type
patient_id
timestamp
payload
```

Regole importanti:

- `schema_version` deve essere supportata dal backend;
- `patient_id` nel topic e nel payload devono combaciare;
- `timestamp` deve essere ISO 8601 con timezone;
- i valori mancanti devono essere `null`, non stringhe `"nan"`;
- `message_id` serve per deduplicare i messaggi QoS 1 o ritrasmessi.

## Persistenza nel database

I messaggi vengono salvati cosi':

```text
edge/status          -> edge_cycles e edge_devices
telemetry/window     -> feature_windows
telemetry/decision   -> decisions
alerts/critical      -> alerts
sensors/watch        -> sensor_status
sensors/ble          -> sensor_status
```

Se arriva uno stato sensore piu' vecchio di quello gia' salvato, il backend non sovrascrive
lo stato piu' recente.

## Eventi interni

Dopo un messaggio salvato correttamente, il backend pubblica un evento interno in memoria.
Per ora serve come ponte verso il futuro modulo WebSocket della D6.

Esempio:

```text
MQTT telemetry/decision salvato
-> evento interno decision_updated
-> in futuro WebSocket verso dashboard medico
```

## Avvio manuale del worker

Per sviluppo locale, Raspberry, VPS o produzione bisogna usare file `.env` locali.
Si parte dagli esempi e poi si inseriscono le password corrette:

```powershell
Copy-Item C:\Users\Daniel\Desktop\ProgettoIoT\cloud\.env.example C:\Users\Daniel\Desktop\ProgettoIoT\cloud\.env
Copy-Item C:\Users\Daniel\Desktop\ProgettoIoT\cloud\backend\.env.example C:\Users\Daniel\Desktop\ProgettoIoT\cloud\backend\.env
```

I file `.env` reali sono ignorati da Git. Il codice non contiene password operative.
Il backend blocca l'avvio in produzione se mancano i segreti o se trova placeholder tipo
`CAMBIA_...`.

Prima avviare broker e database:

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT\cloud
docker compose up -d mqtt postgres
```

Applicare le migrazioni:

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT\cloud\backend
.\.venv\Scripts\python -m alembic upgrade head
```

Avviare il subscriber:

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT\cloud\backend
.\.venv\Scripts\python -m app.mqtt.worker
```
