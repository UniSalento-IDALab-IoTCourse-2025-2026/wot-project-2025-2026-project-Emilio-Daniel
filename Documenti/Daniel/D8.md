# D8 - Logica alert e presa in carico

## Obiettivo

D8 collega davvero l'AI dell'Edge/Raspberry alla dashboard medico:

```text
Raspberry -> MQTT decisione AI -> backend -> alert -> dashboard realtime
```

Il backend non si limita piu' a salvare la decisione, ma crea automaticamente un
alert quando la decisione e' pubblicabile e abbastanza importante.

## Regole sui livelli

| Livello | Comportamento backend |
| --- | --- |
| green | Nessun alert |
| yellow | Visibile come attenzione/dashboard, ma non crea alert urgente |
| orange | Crea alert importante se `should_publish=true` |
| red | Crea alert severo se `should_publish=true` |

Questa scelta evita che ogni oscillazione media diventi una notifica urgente.

## Creazione automatica alert

Quando arriva un messaggio MQTT su:

```text
iot/patients/{patient_id}/telemetry/decision
```

il backend salva la decisione nella tabella `decisions`. Subito dopo controlla:

- `should_publish=true`;
- `level` uguale a `orange` oppure `red`.

Se entrambe le condizioni sono vere, crea un record in `alerts` con stato `new`.

## Deduplica

L'alert automatico usa un `message_id` derivato in modo stabile dal `message_id`
della decisione:

```text
alert-from-decision-<hash>
```

Questo impedisce duplicati quando MQTT QoS 1 riconsegna lo stesso messaggio.

## Categorie alert

Gli alert restano separati per categoria:

| Categoria | Quando viene usata |
| --- | --- |
| clinical | Watch, wearable, battito, SpO2, health |
| behavioral | Pattern di comportamento e routine |
| technical | Edge offline, OAuth, sensori stale, batteria, problemi tecnici |

Se il payload contiene gia' `category`, il backend la rispetta quando e' una delle
categorie valide.

## Presa in carico

Gli stati supportati sono:

```text
new -> acknowledged -> resolved
```

La presa in carico e' idempotente: se un alert e' gia' `acknowledged`, una seconda
chiamata non crea duplicati inutili.

Per `acknowledge` e `resolve` il backend salva:

- utente;
- ruolo;
- timestamp;
- nota, quando presente.

## Realtime

Quando cambia lo stato degli alert, il backend pubblica eventi WebSocket:

- `alert_created`;
- `alert_acknowledged`;
- `alert_resolved`.

La dashboard quindi puo' aggiornarsi senza refresh.
