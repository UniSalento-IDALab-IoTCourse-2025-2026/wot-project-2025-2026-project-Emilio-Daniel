# D10 - Firebase Cloud Messaging

## Obiettivo

D10 collega il backend Cloud alle notifiche push reali di Firebase Cloud Messaging.

Il flusso previsto e':

```text
app Android registra token FCM
-> backend salva token su patient_app_status
-> medico crea task oppure Edge genera alert importante
-> backend crea riga notifications
-> backend invia push reale tramite Firebase
-> app apre/sincronizza task o notifica usando le API REST
```

Il codice usa Firebase reale quando `IOT_BACKEND_FIREBASE_ENABLED=true`. Per i test
locali senza credenziali e' disponibile anche una modalita' fake esplicita, separata
dalla modalita' reale.

## Cosa abbiamo implementato

- Configurazione Firebase nel backend tramite `.env`.
- Invio push reale con `firebase-admin`.
- Creazione automatica di notifica quando il medico crea un task o un messaggio paziente.
- Creazione automatica di notifica quando arriva un alert `orange` o `red`.
- Salvataggio dell'esito tecnico dell'invio dentro `notifications.payload.delivery`.
- Disattivazione del token FCM quando Firebase segnala token scaduto o non valido.
- Modalita' fake per simulare consegna push senza service account Firebase.
- Test automatici senza chiamate di rete reali, usando un sender controllato solo nella suite test.

## Sicurezza

I token FCM e il service account Firebase sono segreti.

Per questo:

- il token FCM viene salvato nel database ma non viene mai restituito dalle API;
- il token FCM non viene scritto nei payload delle notifiche;
- i log salvano solo conteggi ed esiti, non il token;
- il file Firebase service account deve stare fuori dal commit;
- `cloud/firebase/*` e `*service-account*.json` sono ignorati da Git;
- `google-services.json` dell'app Android resta ignorato da Git.

## Aspetto delle notifiche Android

Le push Android usano il canale:

```text
patient_updates
```

Il backend invia a Firebase metadati Android per rendere la notifica piu' curata:

- icona `ic_notification`;
- colore principale `#087F78`;
- priorita' alta;
- visibilita' privata in lock screen;
- canale dedicato agli aggiornamenti paziente.

L'app Android, quando riceve la push mentre e' attiva, usa una notifica nativa con:

- titolo diverso per messaggio, task e alert;
- testo breve e sicuro;
- stile espanso `BigTextStyle`;
- colore diverso per messaggi, attivita' e alert;
- tap sulla notifica che apre l'app e sincronizza i dati.

Il testo completo del messaggio resta dentro l'app dopo login/sincronizzazione, non nella
notifica visibile sul blocco schermo.

## Variabili `.env`

Nel file `cloud/backend/.env`:

```env
IOT_BACKEND_FIREBASE_ENABLED=true
IOT_BACKEND_FIREBASE_FAKE_ENABLED=false
IOT_BACKEND_FIREBASE_CREDENTIALS_FILE=../firebase/service-account.json
IOT_BACKEND_FIREBASE_PROJECT_ID=nome-progetto-firebase
```

Il path e' relativo alla cartella `cloud/backend` quando avvii Uvicorn da li'.

Per testare senza credenziali Firebase:

```env
IOT_BACKEND_FIREBASE_ENABLED=false
IOT_BACKEND_FIREBASE_FAKE_ENABLED=true
```

In questo caso il backend crea la notifica e registra `delivery.provider = "fake"`.
Non viene inviata nessuna push reale al telefono. In produzione questa modalita' viene
bloccata dalla validazione della configurazione.

## Quando parte una push

### Task

Quando un medico/admin crea:

```text
POST /api/v1/patients/{patient_id}/tasks
```

il backend crea una notifica con testo sicuro:

```text
Nuova attivita'
Hai una nuova attivita' da completare nell'app.
```

La push contiene dati tecnici minimi:

```json
{
  "type": "task_created",
  "task_id": "task-123",
  "notification_id": "notification-456"
}
```

### Messaggi medico-paziente

La dashboard invia i messaggi al paziente come task `custom` con:

```json
{
  "kind": "patient_message"
}
```

Il backend li riconosce e invia una push dedicata:

```text
Messaggio dal medico
Apri l'app per leggere il messaggio.
```

Il testo completo del messaggio resta disponibile solo dentro l'app dopo la
sincronizzazione REST. Non viene copiato nel payload delivery e non viene mostrato sulla
schermata bloccata.

La push contiene dati tecnici minimi:

```json
{
  "type": "patient_message",
  "kind": "patient_message",
  "task_id": "task-123",
  "message_title": "Messaggio dal medico"
}
```

### Alert importanti

Quando arriva un alert `orange` o `red`, oppure una decisione AI pubblicabile che genera
alert, il backend crea una notifica generica:

```text
Aggiornamento importante
Apri l'app per verificare un aggiornamento del sistema.
```

Il testo visibile non contiene battito, score AI, stanza o altri dati clinici.

## Stati delivery

Dentro `notifications.payload.delivery` vengono salvati dati simili:

```json
{
  "provider": "firebase",
  "attempted": 1,
  "success": 1,
  "failed": 0,
  "invalid_tokens": 0,
  "last_error": null
}
```

Se non esiste nessun device registrato:

```json
{
  "attempted": 0,
  "success": 0,
  "failed": 0
}
```

In quel caso la notifica resta comunque leggibile dall'app tramite REST.

Con modalita' fake il delivery diventa:

```json
{
  "provider": "fake",
  "attempted": 1,
  "success": 1,
  "failed": 0,
  "invalid_tokens": 0,
  "last_error": null
}
```

## Test locale senza app reale

Questo test verifica tutto il flusso backend senza avere ancora l'app Android/iOS
installata sul telefono. Usa la modalita' fake: il backend non contatta Firebase, ma
simula una consegna riuscita e salva l'esito nel database.

### 1. Configurare fake mode

Nel file:

```text
cloud/backend/.env
```

impostare:

```env
IOT_BACKEND_FIREBASE_ENABLED=false
IOT_BACKEND_FIREBASE_FAKE_ENABLED=true
```

Poi riavviare il backend:

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT\cloud\backend
.\.venv\Scripts\python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8080
```

### 2. Fare login come paziente

In un secondo terminale:

```powershell
$base = "http://127.0.0.1:8080"

$patientLogin = Invoke-RestMethod -Method Post "$base/api/v1/auth/login" `
  -ContentType "application/json" `
  -Body (@{
    email = "paziente.demo@localhost.invalid"
    password = "LA_TUA_PASSWORD"
  } | ConvertTo-Json)

$patientHeaders = @{ Authorization = "Bearer $($patientLogin.access_token)" }
```

La password deve essere quella impostata nel `.env` locale per gli utenti demo.

### 3. Registrare un device finto

```powershell
Invoke-RestMethod -Method Post "$base/api/v1/notifications/devices/register" `
  -Headers $patientHeaders `
  -ContentType "application/json" `
  -Body (@{
    patient_id = "patient-001"
    device_id = "manual-test-device"
    platform = "android"
    app_version = "manual-test"
    fcm_token = "fake-fcm-token"
    notifications_enabled = $true
  } | ConvertTo-Json)
```

Risultato atteso:

```text
patient_id: patient-001
device_id: manual-test-device
status: online
fcm_registered: True
notifications_enabled: True
```

Questo significa che il backend vede un device associato al paziente.

### 4. Fare login come medico

```powershell
$doctorLogin = Invoke-RestMethod -Method Post "$base/api/v1/auth/login" `
  -ContentType "application/json" `
  -Body (@{
    email = "medico.demo@localhost.invalid"
    password = "LA_TUA_PASSWORD"
  } | ConvertTo-Json)

$doctorHeaders = @{ Authorization = "Bearer $($doctorLogin.access_token)" }
```

### 5. Creare un task per il paziente

```powershell
Invoke-RestMethod -Method Post "$base/api/v1/patients/patient-001/tasks" `
  -Headers $doctorHeaders `
  -ContentType "application/json" `
  -Body (@{
    type = "check_in"
    title = "Test notifica fake"
    payload = @{}
  } | ConvertTo-Json)
```

Risultato atteso:

```text
status: created
type: check_in
title: Test notifica fake
```

Quando il task viene creato, il backend crea automaticamente anche una notifica push.

### 6. Controllare la notifica nel database

```powershell
cd C:\Users\Daniel\Desktop\ProgettoIoT\cloud

docker compose exec postgres psql -U iot_backend -d progetto_iot -c "select id, status, title, payload->'delivery' as delivery from notifications order by id desc limit 5;"
```

Risultato atteso:

```text
status = sent
title = Nuova attivita'
delivery = {"provider": "fake", "attempted": 1, "success": 1, "failed": 0, "invalid_tokens": 0, "last_error": null}
```

Se compare questo risultato, il flusso backend e' corretto:

```text
device registrato
-> task creato
-> notifica creata
-> delivery fake riuscita
```

## Prova reale

1. Creare progetto Firebase.
2. Aggiungere app Android con package:

```text
it.unisalento.iotedgecompanion
```

3. Aggiungere anche app iOS con bundle identifier:

```text
it.unisalento.IoTEdgeCompanionIOS
```

4. Scaricare `google-services.json` e darlo a Emilio per l'app Android.
5. Scaricare `GoogleService-Info.plist` e darlo a Emilio per l'app iOS.
6. Creare service account Firebase Admin e salvare il JSON in:

```text
cloud/firebase/service-account.json
```

7. Abilitare Firebase nel `cloud/backend/.env`.
8. Riavviare backend.
9. Fare login nell'app paziente e registrare il device.
10. Creare un task dalla dashboard medico.
11. Controllare che la notifica arrivi sul telefono.
