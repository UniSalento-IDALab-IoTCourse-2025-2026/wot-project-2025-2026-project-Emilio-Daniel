# D9 - Task, test e risultati

## Obiettivo

D9 rende robusto il flusso:

```text
medico crea task -> paziente lo completa -> backend salva risultato -> dashboard aggiornata
```

La base era gia' presente da D5-D7. In questo blocco abbiamo aggiunto regole piu'
rigide su tipi task, scadenze, duplicati e scoring.

## Tipi task supportati

| Tipo | Uso |
| --- | --- |
| `check_in` | Domande semplici sullo stato del paziente |
| `cognitive_test` | Test cognitivo richiesto dal medico |
| `mobility_test` | Test motorio/fisico |
| `medication_reminder` | Promemoria terapia |
| `custom` | Task libero non clinico |

I tipi non riconosciuti vengono rifiutati con `422`.

## Regole ruolo

- `doctor` e `admin` possono creare task.
- `patient` puo' inviare risultati solo per i propri task.
- I test clinici, come `cognitive_test` e `mobility_test`, sono riservati a medico/admin.

## Versione contenuto

Ogni task salva nel payload:

```json
{
  "schema_version": 1,
  "priority": "normal",
  "expires_at": "...",
  "assigned_to": "patient",
  "content": {},
  "scoring": null,
  "medical_note": null
}
```

Questo permette di mantenere lo storico leggibile anche se in futuro cambiamo formato
delle domande o dei risultati.

## Cognitive test

Un `cognitive_test` deve avere almeno una domanda:

```json
{
  "type": "cognitive_test",
  "title": "Test cognitivo",
  "payload": {
    "questions": [
      {
        "id": "q1",
        "type": "text",
        "text": "Colore?"
      }
    ]
  }
}
```

## Scadenza

Se `expires_at`/`due_at` e' passato rispetto a `completed_at`, il backend rifiuta il
risultato con `409`.

Questo evita che un paziente completi in ritardo un test che il medico voleva in una
finestra precisa.

Quando la dashboard legge la lista task, lo stato effettivo viene calcolato: un task
ancora `created` ma con `due_at` passato viene mostrato come `expired`.

## Annullamento

Il medico/admin puo' annullare un task non ancora completato:

```text
PATCH /api/v1/tasks/{task_id}/cancel
```

Il task passa a:

```text
cancelled
```

Un task `completed` non puo' essere annullato. Un task `cancelled` non puo' essere
completato dal paziente.

## Destinatario

Ogni task puo' indicare il destinatario:

```json
{
  "assigned_to": "patient"
}
```

Valori ammessi:

- `patient`;
- `caregiver`.

Questo prepara il flusso in cui alcuni task potranno essere rivolti al caregiver e non
direttamente al paziente.

## Duplicati

Se un task e' gia' `completed`, un secondo risultato viene rifiutato con `409`.

Questo protegge da doppi tap, retry dell'app o invii duplicati.

## Scoring

Lo score viene calcolato solo quando il task contiene una regola esplicita e verificata.
Per ora e' supportata la regola:

```json
{
  "scoring": {
    "type": "exact_match",
    "expected_answers": {
      "q1": "rosso",
      "q2": "4"
    }
  }
}
```

Se non esiste una regola chiara, il backend salva:

```json
"score": null
```

Quando invece lo score viene calcolato, il risultato include anche dettagli leggibili:

```json
{
  "score": 100.0,
  "score_details": {
    "type": "exact_match",
    "correct": 2,
    "total": 2,
    "reason": "2/2 risposte corrette"
  }
}
```

## Risultati strutturati

Il backend salva un `result_type` e organizza `content` in base al tipo task:

- `cognitive_test`: risposte e metadati del test;
- `mobility_test`: durata, passi, distanza, eventuale caduta;
- `medication_reminder`: assunzione farmaco, ora e nota;
- altri task: risposte e nota.

Questo evita di mescolare formati molto diversi nello stesso campo senza contesto.

## Realtime e audit

Quando un risultato viene ricevuto:

- il task passa a `completed`;
- viene salvato `task_results`;
- viene pubblicato evento WebSocket `task_completed`;
- viene scritto audit `task.completed`.
