# D16 - Modello alert composto e workflow lato backend

## Obiettivo

Rendere una segnalazione qualcosa di piu' utile di una singola riga di lista. Il medico
deve poter aprire un alert e vedere contesto, evidenze collegate, azioni disponibili e
storico operativo.

## Endpoint aggiunto

```text
GET /api/v1/alerts/{alert_id}/details
```

L'endpoint e' accessibile a `doctor`, `caregiver` e `admin` se autorizzati sul paziente.
Il ruolo `patient` non puo' leggere il dettaglio workflow degli alert.

## Cosa contiene il dettaglio

Il payload include:

- dati base dell'alert;
- decisione AI collegata, se presente;
- finestra dati collegata;
- task creati come follow-up;
- messaggi/notifiche collegati;
- storico `alert_events`;
- azioni disponibili per ruolo e stato;
- policy di cancellazione.

Esempio sintetico:

```json
{
  "alert_id": "alert-1",
  "status": "new",
  "context": {
    "decision": {
      "decision_id": "decision-3",
      "level": "orange",
      "anomaly_score": 76.5,
      "reasons": ["Wearable fuori routine"]
    },
    "feature_window": {
      "window_id": "window-10",
      "key_features": {
        "heart_rate_mean": 83.0,
        "spo2_mean": 94.0,
        "room_changes": 1,
        "prevalent_room": "kitchen"
      }
    }
  },
  "related_events": [
    {
      "event_type": "alert_created",
      "title": "Segnalazione creata"
    },
    {
      "event_type": "task_created",
      "title": "Follow-up alert"
    }
  ],
  "workflow": {
    "state": "new",
    "available_actions": ["acknowledge", "create_task", "send_message", "resolve"],
    "delete_policy": "permanent_delete_allowed_only_when_resolved"
  },
  "history": [
    {
      "event_type": "acknowledged",
      "actor": "Medico Demo",
      "actor_role": "doctor",
      "note": "Verifico il caso."
    }
  ]
}
```

## Collegamenti supportati

Il backend collega automaticamente:

- `alerts.decision_id` -> decisione AI;
- decisione AI -> finestra feature piu' vicina;
- task con payload contenente `source_alert_id`, `related_alert_id` o `alert_id`;
- notifiche/messaggi con gli stessi riferimenti;
- `alert_events` per presa in carico e risoluzione.

## Cancellazione

La cancellazione definitiva e' permessa solo se l'alert e' gia' `resolved`.

Motivo: un alert aperto o preso in carico non deve sparire dalla dashboard senza storico.
Prima va risolto con nota, poi puo' essere eliminato se serve pulire dati di test.

## Anti-rumore ed escalation

La logica anti-duplicati era gia' presente nell'ingestione MQTT:

- decisioni duplicate con stesso `message_id` non creano righe duplicate;
- alert simili aperti nello stesso intervallo non vengono ricreati.

La logica di escalation resta esposta nel payload alert tramite `escalated` ed
`escalated_at` quando un alert resta aperto troppo a lungo.
